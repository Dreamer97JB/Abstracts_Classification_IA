# Plan 02-03: Methodology schema, outlier handling, and review exports

## Objective

Define a governed methodology contract that follows the client's hierarchy, expose methodology fields in supervised outputs without polluting the theory contract, and generate review artifacts for cases that cannot be assigned safely.

<must_haves>
- Methodology hierarchy is versioned and explicit.
- Methodology fields are separate from theory fields.
- Lack of evidence or conflicting cues produce review/outlier states rather than forced labels.
</must_haves>

<tasks>
<task id="02-03-01">
<title>Create a versioned methodology contract with hierarchy and review reasons</title>
<read_first>
- .planning/phases/02-label-harmonization-and-reviewed-gold-set-assembly/02-CONTEXT.md
- .planning/phases/02-label-harmonization-and-reviewed-gold-set-assembly/02-RESEARCH.md
- requirements.md
- .planning/research/CLIENT_SCOPE_2026-04-02.md
- docs/alcance_cliente/aplicacion_skill_ml_pipeline.md
</read_first>
<action>
Create `configs/methodology.toml` and `src/abstract_classifier/methodology.py` to define the methodology hierarchy exactly as `NN`, `no_empirico`, and `empirico`, with empirical subtypes `cualitativo` and `cuantitativo`. Also define explicit review/outlier reasons for insufficient evidence, conflicting cues, or unsupported methodology patterns. The methodology module should expose load and validate helpers so invalid states such as a subtype without `empirico` are rejected deterministically.
</action>
<acceptance_criteria>
- `configs/methodology.toml` exists
- `configs/methodology.toml` contains `NN`, `no_empirico`, `empirico`, `cualitativo`, and `cuantitativo`
- `src/abstract_classifier/methodology.py` exists and contains a config loader plus validation helpers
- A validation helper rejects a subtype assignment when the primary methodology label is not `empirico`
</acceptance_criteria>
</task>

<action>
Extend `src/abstract_classifier/supervision.py` so the candidate/gold output surface contains separate methodology fields: `methodology_label`, `methodology_branch`, `methodology_subtype`, `methodology_review_required`, and `methodology_review_reason`. Because the current `Seed` and `Muestras` sheets do not include methodology columns, initialize these fields from explicit review scaffolding rather than guessed labels, and generate a separate methodology review queue artifact that analysts can fill or confirm later without touching the raw workbooks.
</action>
<acceptance_criteria>
- The supervised output surface contains the exact columns `methodology_label`, `methodology_branch`, `methodology_subtype`, `methodology_review_required`, and `methodology_review_reason`
- No methodology label is auto-filled from absent workbook columns in `Seed` or `Muestras`
- A separate methodology review export path exists in code
- Rows lacking methodology evidence can be represented without breaking the theory output contract
</acceptance_criteria>
</task>
